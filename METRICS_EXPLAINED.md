# Что означают `c` и RPS в бенчмарке (пояснение к RESULTS_RUNTIMES.md)

Короткий разбор: что за `c` в таблицах, что за число (RPS), и реально ли сервер
обработал «607 запросов в секунду» или это условность.

## `c` — concurrency (одновременные клиенты)

`c=160` значит: бенчмарк-клиент держит **160 параллельных соединений**, и каждое
работает в «закрытом цикле» (closed-loop) без пауз:

> отправил запрос → дождался ответа → **сразу** отправил следующий → … (10 секунд)

То есть в любой момент времени «в полёте» ровно 160 запросов. Это синтетическая
нагрузка — 160 виртуальных клиентов, которые долбят без остановки. Реальные
пользователи так себя не ведут (см. ниже).

## Число — RPS (requests per second), реально посчитанное

Это **не условность**. Бенчмарк буквально считает количество завершённых циклов
«запрос→ответ» за 10 секунд и делит на 10.

`607` значит: за 10-секундное окно сервер реально отдал **~6070 успешных
HTTP-ответов** → 607 в секунду. Каждый ответ — полноценная sync-операция (до
оптимизации **9 SQL-запросов** к Postgres, после — один `pgx.Batch` из 9). Так
что да: **сервер реально обработал ~607 полных синхронизаций в секунду**, а не «в
теории».

## Откуда берётся именно 607 — простая формула

```
throughput (RPS) ≈ concurrency / средняя_латентность_одного_запроса
```

При `c=160` средняя латентность вышла ~264мс (медиана 157мс, но редкие хвосты по
несколько секунд тянут среднее вверх):

```
160 / 0.264с ≈ 607 запросов/с   ✓
```

Отсюда видно: RPS растёт либо от **большей конкуренции** (больше клиентов в
полёте), либо от **меньшей латентности**. Латентность здесь — это в основном
**межконтинентальный RTT ~155мс** (сервер в США, клиент на другом конце планеты),
а не работа сервера. Сам сервер на запрос тратит единицы-десятки мс.

## Что это значит на практике (важно!)

**607 closed-loop запросов/с ≠ 607 пользователей.** Ключевой момент:

- Бенч-клиент шлёт **непрерывно**, без пауз.
- Реальный юзер синкается раз в несколько секунд/минут (открыл приложение,
  поредактировал, свернул — между этим тишина).

Если реальный юзер делает sync раз в ~30 секунд, то 607 синков/с обслуживают
`607 × 30 ≈ 18000` **одновременно активных** пользователей. Поэтому это
«тысячи–десятки тысяч живых юзеров», а не 607.

## Единственная оговорка

Число реальное, но **в конкретных условиях**: этот бокс (RackNerd $20/год, 4
ядра), этот Postgres 18, замер через океан, closed-loop, 10с. Поменяешь
железо/сеть/паттерн — число изменится. Это не абстрактный «рейтинг языка», а
измеренная пропускная под заданным сценарием.

Для честного сравнения важно, что **условия у всех шести рантаймов были
идентичные** (один бокс, один Postgres, один клиент, один свип, равный пул БД=24).
Поэтому **относительные места достоверны**:

```
Django 65 < Dart×1 158 < Dart×4 266 < Rust 409 < Erlang 411 < Go 607   (sync c=160)
```

даже если абсолютные цифры привязаны к стенду.

## Почему latency здесь — НЕ метрика качества сервера

p50 ≈ 155–160мс почти у всех рантаймов — это **чистый RTT туда-обратно через
океан**, а не время сервера. Сервер добавляет единицы-десятки мс поверх. Поэтому
сравнивать рантаймы по абсолютной latency бессмысленно — она у всех одинаковая
(сетевая). Значимые метрики: **RPS (пропускная), доля ошибок и форма кривой** при
росте `c`.
